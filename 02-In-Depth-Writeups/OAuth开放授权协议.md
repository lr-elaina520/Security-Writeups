OAuth 2.0 是一个授权（Authorization）框架，它允许第三方应用在不获取用户密码的前提下，有限制地访问用户在另一个服务上存储的资源。简单说，OAuth 就是让你用“门禁卡”（Token）代替“大门钥匙”（密码）去授权。

例子一：使用 Google 账号登录新闻网站
这是最典型的OAuth 2.0应用，也叫“社交登录”。假设你访问一个新闻网站“News.io”，想用Google账号快速登录。
•	涉及角色：
	你（用户/资源拥有者）：拥有Google账户信息的人。
  News.io（客户端）：想获取你Google基本信息的网站。
	Google（授权服务器 + 资源服务器）：负责认证你，并存储你的信息。
流程如下（基于 Authorization Code 授权码模式，也是最安全的一种）：
1.	请求授权：你在News.io点击“使用Google登录”。News.io将你重定向到Google的授权页面。
2.	用户授权：你在Google页面输入密码登录，并看到一个权限列表（如“查看你的姓名、邮件地址”）。点击“允许”即代表授权。
3.	返回授权码：Google确认后，将你重定向回News.io，并在网址后带一个临时的“授权码”（Authorization Code）。
4.	换取令牌：News.io的后台服务器拿着这个“授权码”和预先在Google备案的“client_secret”，向Google后台换取“访问令牌”（Access Token）。
5.	获取用户信息：News.io使用“访问令牌”向Google请求你的基本信息。Google验证令牌有效后，返回信息。
6.	登录成功：News.io根据获取的信息为你创建或登录账户。
例子二：微信扫码登录第三方网站
这是OAuth 2.0在移动端的经典应用，核心流程与例子一完全一致。
1.	请求授权：你在电脑上访问网站，点击“微信登录”，页面显示一个二维码。
2.	用户授权：你用手机微信扫描二维码，手机微信上弹出授权页面，点击“确认登录”即代表授权。
3.	返回授权码：网站服务器确认你扫码后，从微信后台获取一个“授权码”。
4.	换取令牌：网站后台用“授权码”向微信后台换取“访问令牌”。
5.	获取用户信息：网站用“访问令牌”获取你的微信唯一标识（OpenID）和头像等。
6.	登录成功：网站根据OpenID完成登录。
这两个例子虽然场景不同，但本质上都是OAuth 2.0的“授权码模式”。你可能注意到，整个过程都没有向第三方网站（News.io或电脑网站）输入微信密码




OAuth开放授权就是一个权威的服务器的账号帮你注册另一个网站，不用你输入账号密码

1. 第一阶段：建立“临时通道”（二维码的秘密）
1.	你打开电脑浏览器访问 news.io，点击“微信登录”。
2.	news.io让浏览器重定向到 https://open.weixin.qq.com/connect/qrconnect，并带上一个redirect_uri（告诉微信认证成功后去哪）。
3.	微信后端收到请求后，做了两件事：
	生成一个唯一的二维码票据（ticket），比如 TICKET_ABC。
	把这个 TICKET_ABC 编码成二维码图片，返回给电脑浏览器显示在屏幕上。
4.	同时，电脑浏览器里的前端JS代码（JavaScript） 开始干活了：它启动了一个定时器（轮询），每隔1-2秒就向微信后端发送一个Ajax请求：
“微信大叔，这个 TICKET_ABC 被扫了吗？有人确认登录了吗？”
此时：电脑浏览器和微信后端之间，保持着这个“长连接/定时询问”的通道。

________________________________________
2. 第二阶段：手机App“确认”信号（后端记录状态）
1.	你拿出手机微信，对着电脑屏幕扫码。
2.	手机App读取到二维码里的 TICKET_ABC。
3.	手机App向微信后端发送指令：
“我是用户本人，我确认授权这个 TICKET_ABC。”
此时：微信后端收到手机的指令，把数据库中 TICKET_ABC 的状态从 “待扫码” 修改为 “已授权”。

________________________________________
3. 第三阶段：浏览器“抠出”code（最关键的一步）
就在手机App确认的下一秒（或下两秒）：
1.	电脑浏览器发起的那个定时轮询Ajax请求，刚好到达了微信后端。
2.	微信后端一看：“呦，这个 TICKET_ABC 状态变成已授权了！”于是，它不再返回“未扫码”的等待信息，而是直接返回了一个特殊的HTTP 302重定向响应。
	这个响应里携带的地址是：
Location: https://news.io/callback?code=AUTH_CODE_123
3.	电脑浏览器收到这个302响应后，绝对服从命令，立刻（且自动）发起一个新请求：
	GET https://news.io/callback?code=AUTH_CODE_123
此时：code 是 微信后端通过302响应“塞”给电脑浏览器的，电脑浏览器再带着这个code去敲 news.io 的门。


步骤	谁在操作	具体动作	关键数据流向
1. 请求授权	网站（客户端）	把用户浏览器重定向到微信授权页。	浏览器 → 微信
2. 用户授权	你（用户）	扫码并在微信APP点“确认”。	微信内部确认
3. 返回授权码	微信（授权服务器）	把浏览器重定向回网站地址，URL里带 ?code=xxx。	微信 → 浏览器 → 网站（前端）
4. 换取令牌	网站（后端服务器）	拿着code + client_secret，在后台偷偷请求微信换Token。	网站后端 → 微信后端（这一步用户/浏览器完全感知不到）
5. 获取资源	网站（后端服务器）	拿着access_token去微信API拿你的头像/昵称。	网站后端 → 微信API
6. 登录成功	网站（前端）	根据拿到的头像/昵称，给你创建/登录账号。	网站前端展示



问题1：为啥OAuth要在网站得到code时候，网站还要有一个secret，把这两个发给微信后端，我猜是因为，secret可以让微信知道这个网站是谁，防止任意一个网站都利用这个code得到令牌

第一层：我的猜测（防“任意网站”冒领）
如果没有 client_secret，攻击流程会极其简单：
1.	你在 news.io 点击微信登录，浏览器地址栏变成了 https://news.io/callback?code=ABC123。
2.	攻击者正好在旁边（或者通过浏览器插件）看到了这个 code。
3.	攻击者复制这个 code，打开自己的电脑，伪造一个HTTP请求直接发给微信后端：（这里之所以不直接访问https://news.io/callback?code=ABC123。是因为攻击者想在自己的网站后端得到Token）

POST /token
client_id=news.io
code=ABC123

4.	如果没有 secret：微信后端看到 client_id 是 news.io，code 也有效，就直接把 access_token 返回给了攻击者。
5.	结果：攻击者拿着 access_token 登录了你的账号。
加了 secret 之后：
微信后端要求请求里必须带上 client_secret=xxxxx。攻击者只有 code 和公开的 client_id，但没有 news.io 后台绝密的 secret，请求被直接拒绝。
结论：secret 确保了 “只有真正拥有该网站后台权限的人” 才能用 code 去换 Token。

第二层：更深层设计（隔离“浏览器”与“服务器”）
这是OAuth最精妙的设计之一。code 是在浏览器（前端）地址栏里明文传输的，secret 是永远锁在网站后端服务器里的。
•	为什么 code 可以在浏览器里明文传输？ 因为它是一次性的，且有效期极短（通常5分钟）。更重要的是，光有 code 屁用没有，必须配上 secret 才能换出东西来。
•	为什么 secret 绝对不能出现在浏览器里？ 因为浏览器环境极度不安全（XSS攻击、浏览器插件、恶意脚本都能读取页面源码）。如果 secret 写在前端JS代码里，攻击者偷走 secret 后，就能永久冒充 news.io 网站去请求任何用户的 Token。
所以，OAuth强制把流程拆成两步，核心逻辑是：
1.	浏览器（前线）：只能拿到“一次性临时票据（code）”，这是公开的、易泄露的、但杀伤力极低的。
2.	服务器（后方）：拿着“永久绝密印章（secret）” + “临时票据（code）”，在后台服务器对服务器的加密通道里换 Token。
这个设计的本质是：即使浏览器通道被完全攻破（地址栏被看光、XSS窃取页面），攻击者也只能拿到一个马上过期的 code，而拿不到那个能持续换Token的 secret。



问题2：攻击者正好在旁边（或者通过浏览器插件）看到了这个 code，那攻击者假如直接代替访问https://news.io/callback?code=ABC123怎么办

这正是 OAuth 2.0 在实际攻击中一个非常经典的漏洞利用点！
攻击者根本不需要去碰那个需要 secret 的 /token 接口，他只需要抢在你（正常用户）之前，用浏览器访问那个 https://news.io/callback?code=ABC123 的链接就行了。
这种情况在现实中完全可能发生（比如你点了授权后网络卡顿，或者攻击者通过XSS窃取了地址栏的URL）。

1. 如果网站没做好防护（漏洞状态）：攻击者直接成功
如果 news.io 的开发者没有实现 state 参数校验（这是OAuth最常见的配置缺陷）：
1.	你（受害者）在电脑上点击“微信登录”，浏览器跳转到微信授权页。
2.	你在手机上点击“确认”，微信返回302重定向，浏览器地址栏变成：
https://news.io/callback?code=ABC123
3.	此时攻击者正好在旁边（或通过恶意浏览器插件）抓到了这个完整的URL。
4.	攻击者立刻复制这个URL，粘贴到自己的浏览器地址栏访问。
5.	news.io 的 /callback 接口收到请求后，看到 code=ABC123，它压根不管请求者是谁，直接在后台用 client_secret 去微信换 Token，换成功后，在攻击者的浏览器里写入登录态（Session）。
6.	结果：攻击者的浏览器成功登录了你的账号。你这边再刷新页面，反而会报错（因为 code 已被消耗）。
这就是著名的“授权码拦截攻击（Authorization Code Interception）” + “会话固定/劫持”。
________________________________________
2. 如果网站做了标准防护（安全状态）：攻击者撞墙
OAuth 标准为了解决这个问题，强制要求引入 state 参数。
流程是这样的：
1.	你点击“微信登录”时，news.io 后端生成一个随机字符串（如 STATE_XYZ），存到你的浏览器 Cookie（或Session）里，同时把这个 STATE_XYZ 作为参数一起发给微信：
https://open.weixin.qq.com/...?redirect_uri=...&state=STATE_XYZ
2.	微信在重定向回 news.io 时，原封不动地把这个 state 带回来：
https://news.io/callback?code=ABC123&state=STATE_XYZ
3.	news.io 的 /callback 接口收到请求后，会做一步比对：
o	从你浏览器 Cookie 里读出的 state 值 == URL 参数里的 state 值。
当攻击者复制 https://news.io/callback?code=ABC123&state=STATE_XYZ 到自己的浏览器时：
•	攻击者的浏览器没有 news.io 针对这次登录下发的 state Cookie（因为 Cookie 是绑定域名的，攻击者浏览器里没有这个值）。
•	服务端比对失败，直接返回 400 Bad Request，拒绝用这个 code 换 Token。
结论：state 参数本质上就是把这个 code 跟“发起登录的那台特定浏览器”强行绑定。没有匹配的 state，code 就是废纸。

注意：防止篡改code
总体思路就是，用户请求第三方的时候，网站服务器生成一对身份验证的东西（A和B），然后第三方二维码时候，网站服务器发送B给对方，说这是某某某，然后之后就是普通的生成code之类的，最后服务器换取token时候就是发送code，A之类的给第三方，第三方先看A和B对的上吗，对上了（还有code、secret、client_id对的上吗），成功

也就是说在生成code的时候，第三方会记住这个code是属于谁的


第一步：客户端生成密钥对
一切始于合法客户端（你的网站后端/App）在发起授权请求前，生成一对密钥：
1.	生成 code_verifier：这是一个高强度的随机字符串，长度在43到128个字符之间。它只在客户端本地生成和保存，绝不通过网络发送。
2.	生成 code_challenge：客户端用特定的算法（通常是SHA-256）对code_verifier进行哈希和编码，生成一个“挑战码”。
可以这样理解：code_verifier是唯一的“钥匙”，而code_challenge是根据这把钥匙打造出来的“锁芯”，但无法从“锁芯”逆推出“钥匙”。
🚀 第二步：授权请求中提交“锁芯”
客户端带着这个“锁芯”（code_challenge）和算法标识（code_challenge_method=S256），向授权服务器（如微信）发起授权请求。
此时，授权服务器收到请求后，会存储这个code_challenge和对应的算法，然后生成code并返回给客户端。关键点是：授权服务器此时只存储了“锁芯”，它手里并没有能打开它的“钥匙”。
⚔️ 第三步：用“钥匙”兑换令牌，防御生效
这是验证并防御攻击的关键一步。当客户端拿到code，需要去/token端点兑换access_token时，请求中必须带上最初生成的那个code_verifier（钥匙）。
这时，授权服务器的验证逻辑是这样的：
•	如果请求是合法的（来自真实用户）：授权服务器取出之前存储的code_challenge，用同样的算法（S256）对收到的code_verifier进行哈希计算。如果计算出的新值和存储的code_challenge完全一致，说明“钥匙”配“锁芯”，验证通过，颁发令牌。
•	如果请求是黑客的（拦截了code）：黑客虽然拿到了code，但他的请求中没有合法的code_verifier。因为：
1.	code_verifier从未在网络中传输过，黑客无法截获。
2.	code_verifier是随机生成且一次性的，黑客无法猜测。
3.	code_challenge无法被逆向还原成code_verifier。
因此，黑客发往/token的请求会因缺少code_verifier或code_verifier错误而被授权服务器拒绝
